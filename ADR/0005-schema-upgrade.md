# 0005: Schema upgrade for clean, scalable data

- **Status:** Accepted
- **Date:** 2026-11-27
- **File:** `schema/upgrade.sql` (re-runnable)
- **Run order:** `schema.sql` + `load.sql` (fresh load) → `relationDATA/relationship.sql` → `cleaning/clean_all.sql` → `schema/upgrade.sql`. 35 seconds end to end on a laptop.

## Context

The lab's `schema.sql` permits almost every problem in [0002](0002-data-diagnosis.md). After cleaning ([0004](0004-data-cleaning.md)) the data is clean, but nothing stops new bad data. Kloud Kart takes about 4,000 orders a day and expects flash sales of 400 orders in ten seconds. The brief allows schema changes if documented, and requires the solution to run against a fresh load.

## Decision 1: Leave `schema.sql` and `load.sql` untouched; upgrade in a separate file

| Why | Rejected alternative, and why |
|---|---|
| A fresh load with the lab's own files must keep working. The CSVs are dirty, so strict tables would reject the load. | **Edit `schema.sql`:** the load fails on the first orphan row, unless `load.sql` is also rewritten to use a staging area, which drifts away from the bundle the grader loads. |
| `schema.sql` stays as the evidence of what the database permitted (learning path, chapter 3.1: "read the script first"). | |
| Each change is visible and explained in one place for Nana's team. | |

## Decision 2: What the upgrade changes

| Change | Why (what it prevents or enables) | Rejected alternative |
|---|---|---|
| `bigint` ids on orders, order_items, inventory_log | These tables grow with every sale. Removes the 2.1 billion integer ceiling and matches `place_order`'s `bigint` contract | Keep `integer`: fine for years, but a forced migration later is far more disruptive than now |
| Automatic ids (`GENERATED BY DEFAULT AS IDENTITY`) on all six tables, starting after the current max | No table could create its own key. Writers computed `max + 1`, which collides when 400 buyers arrive at once | `GENERATED ALWAYS`: blocks `race_test.py`, which inserts fixture products with explicit ids |
| `NOT NULL` on every column a row can't make sense without | No more orders without a customer or date, or movements without a product | NOT NULL everywhere: `unit_price` (148 lines under review), `category_id` (race_test fixtures), `parent_id` (roots) are legitimately empty |
| Defaults: `order_date = now()`, `status = 'pending'`, `created_at = now()`, `stock_quantity = 0` | Writers supply only what they know, so there is less room for error | — |
| Value rules: email normalised and well-formed; price > 0; total ≥ 0; unit_price ≥ 0; reason from a fixed list; movement direction matches reason; a category can't be its own parent | Each one is a diagnosis finding that can no longer be written | Enforce in application code: runs only when called; a constraint runs always (learning path, chapter 3) |
| `inventory_log.order_id` + `created_by` | The cleaning could not tell a double entry from a repeat purchase, because movements did not name their order. Now every new sale is traceable to its order and its writer | A separate audit table: duplicates the log and can drift from it |
| Every new sale must name its order (`CHECK … NOT VALID`) | Enforced for all new movements. The 262k historical sales have no order and never will | Validate it: impossible, the history can't be back-filled |
| Order link checked at commit (`DEFERRABLE INITIALLY DEFERRED`) | An order that still has movements can never be deleted, yet one transaction that removes both, as `race_test.py`'s cleanup does, still works | `ON DELETE SET NULL` (tried first): blanks the link and breaks the rule above, so race_test's cleanup failed in testing. `RESTRICT`: also breaks that cleanup |
| `COMMENT ON` key tables and columns | The meaning of `total_amount`, `unit_price`, `stock_quantity` and the log's sign convention lives in the database for the next team | A separate wiki: drifts out of date |

**Deliberately not changed:**
- `timestamp` stays without a time zone. Accra is on GMT with no daylight saving, so this is unambiguous while Kloud Kart operates in Ghana. Revisit if it expands across time zones.
- **No performance indexes yet.** They are added and timed in the performance stage, so the Monday report gets a real before/after.

## Verified (in rolled-back transactions)

- A new order needs no id, date or status. A sale movement linked to it is accepted and records its writer.
- Rejected:
  - a sale with no order
  - a sale with positive quantity
  - an unknown reason
  - an un-normalised email
  - the status `'Completed'`
- A race_test-style fixture (explicit id, no category) is created and cleaned up in one transaction.
- Deleting an order that still has movements is refused at commit.
- Reconciliation KPIs are unchanged: the upgrade changes rules, not data.

## Consequences

- 17 of 18 constraints are validated. The 18th, every sale names its order, applies to new rows only, by design.
- `place_order` must write `order_id` on its sale movement, or the database refuses the sale. That is the intent.
- Writers that send the old status spellings or un-normalised emails will now be refused, and must be updated.
